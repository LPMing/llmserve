# Round 16: ordered ShareGPT prior-prefix bound

`theory/derive.py` scans the committed300-request ordered ShareGPT
token-ID traces and, for every request, finds the longest16-token-block
prefix matching *any earlier request*. It assumes all earlier blocks
remain on the chosen D forever, so finite memory or routing can only
reduce this potential byte saving. The exact input hashes are in
`theory/derive.json`.

| Model trace | Requests with any prior block reuse | Optimistic reused prompt tokens | All prompt tokens | Optimistic byte fraction |
|---|---:|---:|---:|---:|
| Llama-3.1-8B | 32/300 | 19,520 | 257,239 | 7.588% |
| Qwen3-30B-A3B | 32/300 | 20,448 | 258,691 | 7.904% |
| Qwen3-32B | 32/300 | 20,448 | 258,691 | 7.904% |

This is a total-byte bound, **not** an end-to-end latency bound:
queueing near saturation can magnify a small byte change. It does
falsify any claim that the committed traces contain a large reservoir
of unused historical prompt redundancy. A smart D-cache baseline can
achieve part of it. The prior eight-key burst needed for the 100-Gb/s
inversion is absent from these traces. Online placement remains
`NEED_DATA` for a source-backed recurring-prefix workload; fixed-byte
network scheduling remains `NO_GO` by the measured serialization floor.
