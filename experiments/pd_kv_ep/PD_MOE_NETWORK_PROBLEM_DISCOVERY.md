# PD–MoE Network Problem Discovery

Status: bounded search complete — `PD_MOE_NETWORK_PAPER_PROBLEM_FINAL_NO_GO`.
The corrected EP64 controlled result is mechanism evidence only. Two
independent natural Azure windows have matched FAIR/EP_FIRST serving runs and
show no material policy effect. No paper-motivation PASS is claimed.

## Search rule

This bounded search excludes the already-closed generic KV×EP contention,
static priority sweep, DCQCN/QP inheritance, remote-KV/provider-placement, and
the earlier unsupported packet-level mechanisms. It tested whether a
corrected, physically shared S16 network plus model-derived EP64 traffic gives
a repeatable serving-visible result under an unmodified real trace. A
controlled simultaneous-arrival run establishes a mechanism bound, but cannot
by itself establish production motivation.

No synthetic bytes, shortened output, altered arrival times, reduced link
rate, or inferred serving metric is used in the natural-trace run.

## Corrected topology

The earlier S16 network configuration attached each GPU rank directly to a
200-Gbps network link. For eight GPUs/server, that accidentally represented
1.6 Tbps/server rather than the intended two shared 200-Gbps NICs. The new
configuration is separate and does not overwrite the old one:

- 128 GPU-rank endpoints and 32 NIC endpoints;
- each server's eight ranks map four-to-one onto each of two 200-Gbps NICs;
- the server scale-out aggregate is 400 Gbps (50 Gbps/GPU average), while a
  single NIC endpoint remains 200 Gbps;
- 4 leaf / 2 spine, four parallel 200-Gbps links per leaf–spine pair, giving
  1:1 aggregate leaf uplink capacity;
- GPU↔NIC and NIC↔NIC local attachment links are high-capacity local resources,
  not scale-out Ethernet;
- route audit confirms inter-server GPU traffic traverses the Clos and
  same-server traffic remains local.

Artifacts:

## Request critical-path decomposition

Source audit: `Request.set_ttft()` is called at Prefill completion for the
Prefill-side measurement, then Decode `add_done()` overwrites user-visible
TTFT with `decode_first_token_time_ns - arrival`. The request CSV separately
records `prefill_completion_time_ns`, `p2d_kv_ready_time_ns`, the P/D control
handoff (`decode_admit_time_ns`), first actual Decode scheduler admission,
and first Decode token completion. `DecodeScheduler.add_decode()` records the
handoff time; `schedule()` records the first batch admission and its wait.

The exported request-level files are:

- `results/pd_moe_phase_search/REQUEST_CRITICAL_PATH_TRACE.csv`
- `results/pd_moe_phase_search/SERVING_CRITICAL_PATH_BREAKDOWN.csv`

They contain both policies for both natural Azure slices (96 rows each).
The event segments close exactly to CSV TTFT for all 96 rows. P2D KV flows
overlap the arrival-to-Prefill-completion lifecycle and are therefore kept as
a separate event timeline, not added again to TTFT. The last KV completion
precedes the recorded Prefill completion by a median 1.170 ms in the
Conversation window and 1.239 ms in the Code window; the network drain is
hidden by Prefill-side release/compute slack in these samples.

The request CSVs from these two long runs predate the newly added exact
first-batch active-sequence, waiting-queue, batch-size, and decode-token-count
snapshot fields. Those cells remain blank in the exported historical CSVs;
the exporter does not infer internal queue/batch values from request timing.

For FAIR, Decode-ready-to-first-scheduler-batch wait is:

| Natural window | mean | P95 | maximum fraction of request TTFT | requests with any wait |
|---|---:|---:|---:|---:|
| Azure Conversation, 16 requests | 3.064 ms | 5.749 ms | 8.75% | 15/16 |
| Azure Code, 32 requests | 1.885 ms | 5.333 ms | 6.72% | 29/32 |

None of these requests spends at least 10% of TTFT in this admission-boundary
interval. The naturally observed wait is real, but it does not satisfy the
serving-headroom gate. This is also consistent with the prior N1 controlled
boundary audit: its largest fraction was about 6.5%, with a smaller adjacent
point.

## Decode-capacity admission semantics and bounded check

The source audit found that `DecodeScheduler.add_decode()` reserved the
request's Decode KV blocks and unconditionally appended the P/D handoff to
`running`. That bypassed the ordinary `max_num_seqs` admission gate. The
minimal semantics correction now preserves the original request arrival and
ready time, reserves transferred KV at handoff, and places a ready request in
the normal waiting queue only when the configured running-sequence capacity
is full. Queue ordering is by Decode-ready time; actual admission still occurs
through the existing scheduler batch path. This is ordinary baseline capacity
behavior, not a new scheduling policy.

Validation:

- Three focused unit tests pass: saturated slot queues the request; it remains
  queued until a slot is freed; under-capacity handoff keeps the old fast path;
  simultaneous waiters are ordered by Decode-ready time.
- A one-request natural Azure Code FlowSim smoke run is `VALID`: 7,267 input,
  6 output, 714,375,168 generated KV bytes, 480 EP rounds, TTFT 281.173 ms,
  TPOT 1.966 ms, and five token-TBT samples. A rerun with the new batch
  snapshot telemetry reports `running=0` against `max_num_seqs=128` at
  handoff, active sequences 1 at first batch, waiting queue 0, batch size 1,
  and one Decode token in that batch; no capacity-queue entry.
- In the matched natural windows, requests are distributed across Decode
  scheduler instances; every observed instance has peak active population 1,
  versus the configured default `max_num_seqs=128`. These windows do not
  approach a natural capacity knee, so they cannot establish either a
  capacity-induced positive or a universal real-system negative.
- `serving/validate.sh --clocks-only pd pd_per_instance_config moe_pd` reports
  3/3 clock mismatches against committed clocks (−38.08%, −38.08%, −50.56%).
  The worktree already contains broad unrelated modifications, so this result
  cannot be attributed to the capacity change alone. Baselines were not
  refreshed. The capacity-specific unit tests and the actual FlowSim smoke
  pass, but the full behavior drift remains an explicit validation caveat.
- Re-running only `pd` after restoring the old under-capacity status-update
  order yields the same 1,028,919,538 clocks, so the recorded-clock mismatch
  is not caused by the new capacity branch in an under-capacity case. The
  broader pre-existing worktree drift remains unresolved and no baseline was
  updated.

Decision for the tested natural windows: no capacity-knee motivation was
observed; do not lower `max_num_seqs` to manufacture one. The semantics gap is
now represented correctly for future traces that naturally reach the
configured limit.

## Prior bounded negative evidence

- Decode batch-boundary amplification was real but weak and non-monotone:
  the strongest point exposed 6.568 ms, about 6.5% of TTFT; its adjacent larger
  point exposed 1.418 ms, about 1.2%. Low/medium points had no wait.
- Natural P2D handoff-wave analysis did not find a narrow completion cluster.
- Layerwise final-shard delay grew by 23.568% in a prior D64 case, but request
  handoff changed only 0.0115%; prefill release slack absorbed it.
- POST_PREFILL residual-drain penalties were not reflected strongly at serving
  level: D64 K TTFT +4.622% and TBT P99 +0.837%; D32 K TTFT +3.30% and TBT P99
  +0.484%. The KV_ONLY TTFT comparison also changes Decode load and is not a
  clean causal policy comparison.
- The older S16 endpoint model was invalid for shared-NIC claims. Results from
  that topology are not used as corrected-topology evidence.

## Current interpretation

The corrected controlled experiment shows a strong EP/TBT response, while its
P2D KV-ready time is unchanged under EP_FIRST. Both natural Azure matched
pairs (16 Conversation requests and 32 Code requests) show effectively zero
policy effect, including the 9.40-GB Code KV case. Thus the controlled
synchronized result is not reproduced as a natural Azure serving effect.
This does not prove absence under every production trace; it does close the
current EP_FIRST motivation candidate for these two independently selected
natural windows.

## Final bounded decision

`PD_MOE_NETWORK_PAPER_PROBLEM_FINAL_NO_GO`

Across the already-closed candidates and the corrected EP64 natural-trace
checks, network effects have been observed, but none simultaneously provides
≥20% network-critical optimization headroom and ≥10% integrated TTFT/TBT/TPOT
headroom under the tested realistic, model-derived workloads. P6's large
controlled result depends on aligned cohorts and does not recur in either
natural Azure window. P3 now has ordinary capacity semantics, but the tested
natural windows remain far below configured per-scheduler capacity; no
capacity claim beyond those windows is made.

No further pressure escalation is justified from current evidence. Reopen only
if a newly available production trace/configuration naturally supplies a
specific untested dependency (e.g. real capacity saturation or a trace-native
barrier-critical EP interval); do not manufacture one by reducing limits,
changing link rate, or aligning arrivals.
