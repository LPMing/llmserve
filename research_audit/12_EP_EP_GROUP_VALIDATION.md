# EP–EP independent-group validation (2026-10-11)

## Decision in one sentence

Two independent, legal EP4 Decode groups can now be represented by the
integrated FlowSim topology and do contend on shared directed 200-Gbps
server–ToR links, but under the tested Qwen3/TP2 workload that contention
changes collective latency by only 1.6–6.4% and token latency by under 1%; it
does not establish useful scheduling headroom. This closes the previously
conditional EP–EP representability check as a **capability PASS / motivation
NO-GO** for this tested operating point.

This is not a universal claim that EP groups never interfere. It is a bounded
result for the exact topology, model, collective realization, request shape,
and FlowSim service model below.

## What was added and correctness scope

`serving/core/config_builder.py` now derives grouped topology dimensions when
there are multiple independent `dp_group`s, or when one Decode group coexists
with a multi-lane Prefill/shadow-rank prefix. The latter condition was added
after the first A-only control exposed a second shape bug: the old single-group
path produced 12 configured ranks but only 8 topology coordinates. The fixed
grouped builder produces `[2, 2, 3]` for that control and `[2, 2, 6]` for the
two-group run; in each case dimensions multiply to the configured logical
rank count. Unsupported/interleaved layouts still fail closed.

The generator is
[`generate_two_decode_ep4_groups_flowsim.py`](../experiments/pd_kv_ep/configs/generate_two_decode_ep4_groups_flowsim.py).
Each Decode EP4 group has two TP2 Decode instances, one on D0 and one on D1;
the two groups are separated in logical collective lanes. The explicit
`flowsim_rank_map` places both groups on the same physical D0/D1 servers and
same rail-0 directed links. Each server has eight GPU endpoints and two
200-Gbps NIC-facing links in the topology, with the local GPU fabric modeled
separately. Prefill shadow receiver ranks alias their paired physical Decode
GPU endpoints; they do not create extra physical GPUs or NIC bandwidth.

The event ledger reports four participants and twelve peer flows per EP4
collective. Requests sharing one group are represented by the same physical
group collective with a `request_ids` set; the experiment did not split a
batched collective into invented per-request flows. The implementation's
collective semantics are still ALLGATHER dispatch plus REDUCESCATTER combine,
with BALANCED expert routing—not strict GateRouter A2A_P2P. The result is
therefore specifically about the currently implemented AG/RS group traffic.

## Matched experiments

All requests use Qwen3-30B-A3B-Instruct-2507, TP2 instances, model/profile-
derived communication, input 128 tokens, output 32 tokens, arrival 0, no
prefix cache, no chunked prefill, FlowSim FAIR, and the existing one-ToR
topology with 200-Gbps physical scale-out links. No byte override, added delay,
bandwidth reduction, or arrival synchronization beyond the explicitly
controlled all-at-zero workload was used.

| Comparison | Shared groups / active requests | Dispatch CCT mean (P99) | Combine CCT mean (P99) | TTFT | TPOT and per-token TBT/ITL |
|---|---:|---:|---:|---:|---:|
| Group A, isolated → two groups | 2 requests/group; 2 → 4 total | 10.897 → 11.593 µs (**+6.39%**) | 10.364 → 10.528 µs (**+1.58%**) | 43.051 → 43.051 ms (**0%**) | 5.478528 → 5.519808 ms (**+0.75%**) |
| Group A, isolated → two groups | 4 requests/group; 4 → 8 total | 10.897 → 11.593 µs (**+6.39%**) | 10.528 → 10.856 µs (**+3.11%**) | 44.873 → 44.873 ms (**0%**) | 6.108400 → 6.157552 ms (**+0.80%**) |

Each reported CCT mean/P99 is based on 1,488 completed collective-round
observations per phase and group. In these deterministic homogeneous runs,
all observations in a given phase had the same CCT, so P99 equals the mean;
this is **not** evidence of a broad or random tail distribution. The two
request-level serving samples in the smaller comparison, and four in the
larger comparison, likewise do not support population-level percentile or SLO
claims. All output tokens in each matched request had the same recorded ITL.

The larger 8-request FULL run also completed all requests: TTFT 44.873 ms,
TPOT 6.157552 ms, 31 recorded ITLs/request, and 0.235757112 s simulator time.
The 4-request FULL run completed at 0.214165048 s simulated time; the
matched 2-request A-only run completed at 0.212885368 s. These are simulated
serving latencies, not wall-clock runtime. Wall time for each bounded run was
about 25–53 s depending on telemetry volume.

### Communication accounting

At 128 input tokens, Qwen3's configured KV geometry yields
`128 × 48 × 2 × 4 × 128 × 2 = 12,582,912 B/request`. This is generated by the
model and current KV dtype; it is not an override. Thus each request-count
change also changes the corresponding real P2D work, but the Decode-side
per-group EP workload is held matched: two or four Decode requests/group in
both FULL and A-only conditions. Each group round reports four participants
and twelve peer flows; the collective ledger reports 4,352 B/participant for
ALLGATHER dispatch and 4,096 B/participant for REDUCESCATTER combine. The
workload runs 1,488 rounds/phase/group (`31 output ITLs × 48 layers`). These
are native simulator collective inputs/ledger fields, not a claim of strict
GateRouter A2A or a separately measured packet-wire byte total.

### Collective-to-token attribution

The measured TBT delta is not just correlated with the collective change. The
Qwen3 run emits one dispatch and one combine collective in each of 48 layers
per Decode iteration. For the 2-requests/group point, the added CCT per layer
is `(11.593−10.897) + (10.528−10.364) = 0.860 µs`; across 48 layers this is
`41.280 µs`, exactly the observed TPOT/TBT increase
(`5.519808−5.478528 ms`). For the 4-requests/group point it is
`(11.593−10.897) + (10.856−10.528) = 1.024 µs/layer`; across 48 layers this
is `49.152 µs`, exactly the observed delta (`6.157552−6.108400 ms`). Thus the
simulator propagates the per-layer network delay to the token barrier. The
end-to-end percentage remains small because the accumulated 41–49 µs is only
about 0.75–0.80% of a 5.5–6.2 ms token interval—not because the measured
network effect vanished before the barrier.

## Network attribution

The two groups' D1→D0 collectives map to common directed links
`28→30→26`; the reverse direction uses `26→30→28`. The full-run event/path
telemetry showed simultaneous group traffic on these shared links, up to
eight active EP peer flows in aggregate. The peak FlowSim residual-fluid
backlog on a shared directed link was approximately 33.9 KiB and utilization
reached 1.0 during active service. This backlog is an **analytical fluid
backlog**, not packet-buffer occupancy, ECN, PFC, or packet loss.

The tested requests all completed P2D before Decode EP began; no KV flow was
active in the EP window. This is an EP–EP experiment, not a KV–EP result. The
measured CCT increase is consistent with cross-group sharing of the common
directed cut. Per-layer dispatch+combine deltas sum exactly to the measured
per-token TBT delta across all 48 layers, so the network effect reaches the
Decode barrier. Its total contribution remains below 1% of each token interval
in these configurations.

## Reproduction and retained evidence

Run the generator from the repository root:

```bash
python experiments/pd_kv_ep/configs/generate_two_decode_ep4_groups_flowsim.py
```

Use the same serving command for each row below, substituting the indicated
config, workload, request count, output path, and run id. The generated input
files and their SHA-256 hashes are recorded in
[`01_REPRODUCIBILITY.md`](01_REPRODUCIBILITY.md) and the refreshed provenance
manifest.

```bash
timeout 180s env PYTHONPATH=.:/tmp/llmsim-chakra-shim.TzDOXs \
PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python \
FLOWSIM_MAX_TELEMETRY_ROWS=200000 \
FLOWSIM_MAX_FLOW_TELEMETRY_ROWS=200000 \
/home/lpm/.conda/envs/llmsim-flowsim/bin/python -m serving \
  --cluster-config <CONFIG> --dataset <WORKLOAD> --num-reqs <N> \
  --network-backend flowsim --request-routing-policy RR \
  --max-num-seqs 8 --max-num-batched-tokens 512 \
  --no-enable-prefix-caching --no-enable-chunked-prefill \
  --log-level WARNING --log-interval 60 --run-id <RUN_ID> \
  --output <REQUEST_CSV> --flowsim-telemetry <TELEMETRY_JSONL>
```

## Gate update

- **Topology / group representation:** PASS for the supported rectangular,
  group-major layout; all ten focused regression scripts pass (36 tests).
- **Physical shared-link contention:** PASS in the full two-group FlowSim run.
- **EP–EP network effect:** present but modest: dispatch +6.39%, combine
  +1.58–3.11% for the matched cases.
- **Serving-barrier effect:** weak: TTFT unchanged; TPOT/TBT +0.75–0.80%.
- **Priority/oracle headroom:** not run. The motivation gate is not met.
- **Packet-level corroboration:** not run. Because the integrated serving
  effect is below 1%, a packet-level replay would not answer the currently
  gated scheduling question and is not justified in this bounded phase.
- **Paper direction:** `NO_GO` for the proposed fine-grained network
  scheduling paper based on this evidence. Preserve this as a capability and
  negative motivation result; do not scale requests or intensify load to
  manufacture a larger number.
